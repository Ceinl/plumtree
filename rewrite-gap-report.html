TL;DR — was it nicer before?

Short answer: the internals are much better now; the product surface is smaller. The rewrite traded the old "everything works end-to-end but glued together with tokens and a browser flow" for a genuinely clean identity/config/storage core — but the headline feature (run any deployed app with plain ssh) is currently not wired into the production server on main.

The one-sentence verdict

Main is a mid-cutover snapshot: an excellent control plane (pairing, devices, SQLCipher, audit, typed config) with no leaf. The old tree could actually serve apps to end users over SSH; today's plumtree serve only accepts author/pairing traffic and /api/v1. The code to fix this exists on unmerged branches (origin/issue-140-leaf, origin/issue-143-e2e).

▲ Clearly better after the rewrite

  • Identity: per-device Ed25519 pairing + bootstrap authority + device invitations + recovery phrase replaces shared deploy tokens
  • Storage: strict SQLite/SQLCipher repository with quotas, budgets, audit trail (old: JSON snapshots)
  • Config: typed server config + config show/set/unset (old: loose JSON + flags + env soup)
  • SDK: typed operation packages (sdk/kv, sdk/bus, …) instead of one flat god-package
  • Hygiene: single root module, no cross-module legacy shims, ABI v4 preserved with compat fixtures, tests green

▼ Lost or broken vs. before

  • No hosted run path on main — gateway never assembled by cleanrole; ssh owner/app@host is aspirational
  • Sandboxed server-side builds deleted (build-worker) — deploy now requires a local Go toolchain
  • Dashboard / claim pages / anonymous preview / live-apps SSE stream all gone with the HTTP API
  • --access restricted is decorative — nothing enforces it at connect time
  • Suspension kill-switch has no trigger — repo supports it, no operator command calls it
  • KV still JSON-file-per-app, outside the new encrypted SQLite story

⟳ Feels different, netural swap

  • pt claim+Shoo browser auth → pt pair/recover SSH subsystem (better security, worse discoverability)
  • PLUMTREE_SERVER_URL/DEV_TOKEN env overrides → paired-server store
  • Server-side build → local pt build
  • tui-runtime public module → private sdk/internal/tui; authors get the declarative sdk/ui node tree instead of raw components
  • Multi-container compose (5 services) → single root-owned process (control role only)

Your instinct, quantified

Of the ~40 discrete user/operator-facing features in the old tree, roughly 25 carried over intact or improved, 9 were intentionally removed as part of the clean-break design (documented), and ~7 were dropped or orphaned with no replacement and no documented decision — those are the ones making it feel like something's missing. The biggest single gap (leaf serving) already has a merged-quality branch waiting.

Architecture: before → after

The rewrite collapsed six Go modules into one root module plus the SDK, and swapped the transport from HTTP+SSH hybrid to SSH-only.

Before — strengths
Working end-to-end product (deploy→claim→run). Server-side builds meant zero local toolchain. Dashboard made apps discoverable. Anonymous preview let strangers try public apps.
After — strengths
One trust model (SSH keys everywhere). Encrypted at-rest metadata+artifacts. Typed config, audit log, quotas/budgets enforced in-repo. Much smaller attack surface (no HTTP listener at all).

Issues found in current main

Found by direct inspection while mapping features. Build/vet/test are all green — these are logic, wiring, consistency, and documentation problems, not compile errors.

1. critical Restricted access mode never enforced at connect time internal/sqlite/repository.go:674 · internal/gateway/session.go:158

ResolveRunnable loads access_mode but only acts on suspension. No access-key/fingerprint gate exists between an SSH connection and a restricted app anywhere in the gateway or (future) leaf role. Once issue-140 merges, every app is effectively public regardless of manifest.

Add the access-key admission check in ResolveRunnable (or a gateway middleware) before merging leaf serving — ideally as part of issue-140 review.

2. critical README security-model describes deleted architecture README.md:178–183

"Build is sandboxed too… builds happen in isolated workers — no secrets, no default network, bounded CPU/memory/disk… checksum + module policy enforcement" — the build-worker was deleted in #97; builds are now plain local go build (internal/build/build.go). "Production runners are separate worker processes from the control plane" — production serve contains no runner at all on main. The capability table promises Env/Fetch for claimed apps that aren't reachable in production.

Rewrite Security model + How-it-works to match reality (local build, control-role-only serve), or mark aspirational items explicitly as gates like the leaf sentence does.

3. high pt help errors for most commands internal/cli/workflow/help.go:69

Help topics exist only for new/dev/deploy/secret/egress/access. pt help status, pt help app, pt help logs, pt help audit, pt help ssh, pt help server, pt help device, pt help pair, pt help recover all return unknown pt help command — even though the commands exist. Old pt printed one comprehensive usage covering every command + env vars.

Add topics for all 16 commands; include subcommand grammars (server/device/app) and the --yes/confirmation semantics.

4. high SSH sessions always report exit-status 0 internal/gateway/session.go:207

After every session — including error/cancel paths — the gateway sends exit-status 0. Scripts doing ssh app@host ... || alert can't detect failure. Notably, a local branch issue-127-ssh-exit-status exists addressing exactly this and remains unmerged.

Merge/resurrect issue-127; plumb real exit status (and consider an "extended failure" exit code for platform-side errors vs guest errors).

5. medium Dead administrative surface: suspensions & quotas operators can't reach internal/sqlite/repository_operations.go:426,701

SetDeploymentSuspended and SetQuota have no non-test callers. Moderation is impossible in practice: no plumtree suspend …, no config-driven default quotas surfaced beyond defaults. (Old server had working suspension endpoints.)

Operator subcommands in cleanrole + optional config fields for default author quotas.

6. medium Two storage engines, weaker half carries app state internal/gateway/caps.go:34–54

Guest KV — the primary durable state for every deployed app — uses per-app JSON FileStore under StateDir/kv while everything else moved to strict SQLCipher. Loses at-rest encryption, transactional guarantees, and the integrity verification the new repo applies to artifacts. Also lazily created per gateway process: multiple gateway processes would fork KV state (bus is documented in-memory; KV is not).

Move KV into the repository (schema already has budgets/quota patterns), keep FileStore only for pt dev.

7. medium ID generation silently degrades to constant on rand failure internal/httpapi/v1/server.go:726–731

newID returns prefix+"_fallback" if crypto/rand.Read fails instead of erroring. Two concurrent creations would collide on the primary key; also IDs become predictable in that regime.

Propagate the error; callers already have problem-response paths.

8. medium Every API request does 3–4 sequential auth queries internal/httpapi/v1/server.go:157–178

authorize fetches ServerIdentity + Device + Author on each request, and version route hits it twice logically (route + handler). Fine at current scale; the repo has performance-budget CI for a reason.

Cache server identity at startup (it's immutable per process); consider short-TTL device cache.

9. medium Example "Try it" instructions can't work README.md:114–117, examples/*

All four examples advertise ssh <owner>/chat@plumtree.app etc. No production host serves apps on main (and plumtree.app isn't this repo's deployment). New-author onboarding following the README dead-ends at step "Run".

Either qualify the lines ("once leaf serving ships") or point at the local journey: pt dev --ssh + ssh -p 2222.

10. low Gateway knobs unreachable from typed config internal/server/config/ vs internal/gateway/server.go:38–52

RunnerWorker, RunnerEndpoint/Token, AllowHostCommands, MaxConcurrentSessions tuning, idle/handshake timeouts — none appear in serverconfig fields. When the leaf role merges these will need names, validation, and docs; deciding them now avoids config churn.

Pre-register the config schema fields (hidden/disabled) as part of issue-140.

11. low controlclient is an unfinished seam internal/gateway/controlclient/client.go

A 229-line HTTP client toward the old-style control backend exists but satisfies no production path; the Backend interface comment even describes the embedded vs out-of-process duality that main doesn't realize yet. Risk: bitrot before split deployments return.

Either finish it with issue-143 journeys or move it behind the leaf branch until needed.

12. low Session-log truncation is silent to the reader internal/gateway/session.go:200–206

RecordSessionLog(sessionID, log, truncated) records truncation, but pt logs consumers get no marker in-band; debugging long sessions may mislead.

Prefix stored logs with a truncation notice, expose truncated flag in pt logs output.
